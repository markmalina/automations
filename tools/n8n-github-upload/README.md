# Work → n8n → GitHub

Задача: https://github.com/markmalina/freelance/issues/8

**Статус: BLOCKED_DEPLOYMENT_ACCESS. Рабочий загрузчик не развёрнут и не принят.**
Здесь подготовлена первая контрольная точка: защищённый бинарный roundtrip Work → настоящий n8n → Work. Это не workflow публикации в GitHub.

## Что установлено

- Текущая обычная Work-среда исполняет команды; доступны Python, curl и git.
- Программный HTTPS POST 1024 бинарных байтов на httpbin.org выполнен, возвращённые байты совпали по SHA-256. См. `http-binary-probe.json`. Сервис использован только для синтетического теста, в рабочую архитектуру не входит.
- HTTPS к docs.n8n.io и api.github.com доступен. Это не гарантия доступности будущего адреса n8n или следующих Work.
- GitHub connector видит приватный `markmalina/freelance` и имеет push-доступ. Его авторизация не передаётся автоматически git в Work или n8n.
- Адрес существующего n8n и разрешённый канал его администрирования не обнаружены. Railway plugin не подключён; в переменных текущего процесса нет имён N8N/RAILWAY/GITHUB_TOKEN. Значения других секретов не читались.
- В Ops найдены фиксированные цели других проектов; готовой цели Freelance/n8n нет. Их credentials не использованы.
- Docker и n8n в текущей Work-среде не установлены. Образ, импорт workflow и его исполнение здесь не проверены.

## Состав

- `probe.workflow.json`: неактивный workflow из штатных Webhook и No Operation; Header Auth; возвращает принятые бинарные данные.
- `probe_work.py`: одноразовая диагностика настоящего n8n из обычного Work; без Base64, ZIP, LLM и вывода секрета.
- `Dockerfile`, `compose.yaml`, `.env.example`: кандидат самостоятельного размещения n8n с постоянными томами. Не развёрнут.
- `DESIGN.md`: требования к будущему процессу на штатных узлах, Git и восстановлению.
- `RAILWAY_RESEARCH.md`: углублённое исследование существующего Railway, сна, ресурсов, цены, готовых шаблонов и границ постоянного Work-подключения.
- `RUNBOOK.md`: настройки, запуск первой проверки и передача следующему Work.
- `VERIFICATION.md`: факты, ограничения и незавершённая приёмка.

## Размещение и стоимость

После углублённого исследования и уточнения владельца **рекомендуется существующий Railway workspace: один отдельный service n8n-upload, один persistent volume, SQLite, одна replica, regular mode**. Отдельный VPS, Redis, PostgreSQL service и подписка n8n не требуются для начала. Нужен административный доступ к точному Railway target и согласование дополнительных расходов до создания ресурсов.

Обычный запущенный n8n занимает память в простое. Railway Serverless может останавливать сервис через 5–10 минут без исходящего трафика и будить запросом; работу сна с n8n нужно доказать измерениями. Диск остаётся оплачиваемым. Шаблоны одного service уже существуют, но опубликованный template не равен проверенному развёртыванию.

Добавление service в существующий workspace не создаёт вторую абонплату Hobby $5; usage увеличивается. При условных 0.5 GB RAM, 0.02 vCPU среднего CPU и 1 GB данных постоянная работа даёт около $5.55/месяц. Сон может сильно уменьшить compute, но фактический расход не измерен. Полные ставки, сценарии и ограничения — в RAILWAY_RESEARCH.md. Тариф и текущий bill аккаунта не проверены; прежний реестр Ops содержит только исторический Hobby.

Найден документированный механизм network secrets/Personal vault для Codex Cloud environments. Его применимость к текущему обычному Work ещё не доказана; это не считается выполнением требования «без отдельной задачи Codex Cloud для каждой загрузки».

Уточнение 06.11: в текущем аккаунте обычного Work фактически открыта форма пользовательского MCP с OAuth. Предложена схема постоянного OAuth-подключения n8n и краткоживущего upload grant через JSON MCP, с передачей файлов напрямую по HTTPS. Это устраняет необходимость постоянного webhook token в каждом executor на уровне проекта решения; живое испытание ещё требуется. Подробности и точное действие для подключения Railway — в `AUTH_FOLLOWUP_2026-11-06.md`.

## Для продолжения

Нужен один конкретный доступный target: существующий self-hosted n8n с HTTPS и административным каналом либо сервер/проект, где разрешено его разместить. Если размещение добавляет расходы — сначала согласовать бюджет. Затем обеспечить скрытую привязку секрета Webhook к Work и повторить её проверку в новом Work. Не просить публиковать секрет в сообщении, issue или репозитории.

Исходные требования владельца и критерии приёмки сохранены в issue #8. Баннеры Dreame и issue #7 не затрагиваются.
