# Размещение Work → n8n → GitHub на существующем Railway

Исследование: 05.11.2026. Задача: https://github.com/markmalina/freelance/issues/8. Это исследование и план, не подтверждение развёртывания.

## Решение

Рекомендация: **один отдельный service `n8n-upload` в существующем Railway workspace**, при необходимости в существующем project, с **одним persistent volume**, встроенной **SQLite**, одной replica и включаемым после проверки **Serverless**. Отдельный VPS покупать не требуется. Redis, отдельный PostgreSQL, queue workers, S3 и LLM для начальной нагрузки не нужны.

Это отдельный контейнер внутри уже используемой платформы, а не новая подписка на сервер. На Railway подписка относится к workspace, а потребление добавляется к общему usage. Новый service не означает ещё одну плату Hobby $5; но добавленные RAM/CPU/диск/трафик не становятся бесплатными. Источники: [Railway pricing](https://docs.railway.com/pricing), [services](https://docs.railway.com/services).

Размещать n8n вторым процессом внутри Gate технически возможно только после изменения его образа и запуска, но для этой задачи не рекомендуется: общий жизненный цикл, память и права, зависимость от работы Gate, невозможность независимо усыплять n8n. Отдельный service позволяет раздельно перезапускать и измерять загрузчик. Это архитектурный вывод, а не ограничение Railway.

## Что известно о нашем аккаунте

В актуально прочитанном реестре Ops зафиксирован **исторический** Hobby с базой $5/месяц; последняя отражённая оплата $22.13 от 17.10.2026. $25/месяц там обозначены как предложение резерва, а не установленный hard limit и не разрешение потратить эту сумму. Источник: [registry.json](https://github.com/markmalina/ops/blob/main/docs/infrastructure/registry.json).

Текущие billing, остаток кредитов, расход сервисов, тариф, список проектов, фактический свободный лимит и настройки сна в кабинете Railway **не прочитаны**: административный канал сейчас не подключён. Проект и environment нельзя выбирать по названию или по старому Telegram Gateway. Gate/AQUB credentials не используются для нового n8n.

В прочитанном Ops есть фиксированные цели других проектов, но нет готовой Freelance/n8n цели. Для существующего управляемого контура нужно подготовить отдельную точную цель и канал развёртывания; готовый пользовательский Telegram-сервис не является универсальным хостом.

## Память и сон: где прав пользователь

Railway оплачивается по фактическим ресурсам, но **ожидающий HTTP-запроса n8n остаётся процессом и занимает RAM**. Пиковый предел RAM не равен фактическому расходу, а отсутствие загрузок не равно отсутствию процесса.

Serverless останавливает неактивный контейнер; входящий запрос запускает его. Текущий reference описывает 5 минут без исходящих пакетов и интервальную проверку: на практике сон через **5–10 минут**. Другая официальная статья округляет это до 10 минут; для расчёта безопаснее брать 10. Включение применяется к новому контейнеру после deployment, а не немедленно к уже работающему.

Первый запрос может задержаться или получить 502. Поэтому перед отправкой 30 MB клиент должен обратиться к готовности `/healthz/readiness`, дождаться готового сервиса с ограниченными повторами, и только затем передавать комплект. Это проектное решение; ещё не проверено на нашем n8n. Не делать постоянный внешний uptime polling, иначе он сам будет мешать сну.

Источник: [Serverless reference](https://docs.railway.com/deployments/serverless). Сон экономит compute, но не отменяет хранение постоянного диска и действующую базовую подписку.

### Что может удерживать n8n бодрствующим

- Открытый редактор с активными запросами/соединениями.
- Polling workflows, обращения к другим API, проверки сервиса каждые несколько минут.
- Сетевые соединения с PostgreSQL/Redis и фоновые задачи.
- Телеметрия, проверки версий, получение шаблонов; частота каждого механизма разная. Сам факт фоновой функции ещё не доказывает, что сна не будет.

Для начала использовать локальную SQLite, только Webhook workflow, выключить диагностическую телеметрию, version notifications и templates. Это уменьшает известный фоновый трафик, но **не гарантирует сон**: нужны метрики и фактический переход service в sleeping. При серверном сне расписания внутри n8n не считать надёжным источником пробуждения; для загрузчика они не нужны. Источники: [n8n isolation](https://docs.n8n.io/hosting/configuration/configuration-examples/isolation/), [n8n telemetry](https://docs.n8n.io/hosting/securing/telemetry-opt-out/).

## Что взять готовым

| Вариант | Что даёт | Решение для этой задачи |
|---|---|---|
| Официальный n8n Docker image | Штатный движок, Webhook, файловые и Git nodes | Предпочтительная основа, закрепить проверенную версию |
| Railway single-service SQLite template | Один n8n, volume, URL и первоначальные настройки | Использовать как образец конфигурации после проверки конкретного template |
| n8n + отдельный PostgreSQL | Дополнительный сервис и сетевые соединения | На старте не требуется |
| n8n + PostgreSQL + Redis + workers | Очередь и масштабирование нескольких исполнителей | Для 100 файлов / 30 MB избыточен |
| n8n Cloud | Управляемая подписка n8n | Не выбран для обычного Git и постоянных рабочих копий |

Реальные готовые варианты: [single service](https://railway.com/deploy/n8n-10), [SQLite Lite](https://railway.com/deploy/n8n-7), [Postgres](https://railway.com/deploy/n8n-5), [workers](https://railway.com/deploy/n8n-4). Это опубликованные авторами templates на площадке Railway, а не прошедшие нашу приёмку компоненты. У некоторых описания и теги версий расходятся; встречаются устаревшие Basic Auth variables. Не запускать template вслепую и не брать плавающий `stable` как воспроизводимую фиксацию версии.

Для внутреннего маршрута достаточна бесплатная self-hosted Community edition. Платная функция n8n «Version control using Git» относится к хранению и переносу самих workflow; она отличается от штатного **Git node**, используемого для файлов пользователя. Enterprise binary S3 storage для этого маршрута не требуется. Источники: [editions](https://docs.n8n.io/hosting/community-edition-features/), [Git node](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.git/).

## Ресурсы и постоянный диск

Предлагаемая стартовая конфигурация для проверки: **1 replica, regular mode, предел RAM 1 GB, предел CPU около 1 vCPU, один volume с начальным доступным объёмом 1–2 GB**. Это инженерный стартовый выбор, не измеренная потребность и не гарантия, что хватит для любого репозитория. При OOM сначала проверить бинарный режим и параллелизм, затем по результатам обоснованно увеличить RAM. Размер Git clone зависит от репозиториев и истории, а не только от 30 MB текущей загрузки.

`N8N_DEFAULT_BINARY_DATA_MODE=filesystem` нужен, чтобы бинарные данные не держались целиком в стандартном memory storage n8n. Это не превращает всё выполнение в zero-copy: manifest, HTTP parser, хеширование и упаковка Git тоже требуют памяти. Источник: [binary data](https://docs.n8n.io/hosting/scaling/binary-data/).

На диск попадают временный binary storage n8n, staging текущего комплекта, рабочее дерево, Git objects и временный packfile. Это несколько представлений данных. Не считать, что комплект 30 MB потребует строго 30 MB диска. Для 100 загрузок по 30 MB уникальные бинарные данные могут добавить около 3 GB ещё до дополнительных копий и backups; сжатые JPG/PNG/PDF не обязаны сильно сжиматься в Git. Очистка staging не удаляет историю Git.

Railway разрешает один volume на service; replicas с ним не поддерживаются, redeploy может дать короткий простой. Диск оплачивается по использованному объёму; snapshots оплачиваются отдельно по фактическому уникальному хранению. Для одного последовательного загрузчика это допустимо. [Volume reference](https://docs.railway.com/volumes/reference).

### Предлагаемая раскладка одного тома

Mount `/data`:

| Путь | Назначение | Восстановление |
|---|---|---|
| `/data/.n8n/` | SQLite, настройки, credentials storage | Backup плюс прежний encryption key |
| `/data/work/git/<repo-id>/<branch-key>/` | Git clone/worktree | Можно заново получить из GitHub |
| `/data/work/uploads/<upload-id>/` | Байты незавершённого комплекта | Сохранить до подтверждения/явного срока хранения |
| `/data/work/receipts/` | Дополнительные durable receipts, если выбран файловый журнал | Backup; при неизвестном результате сверить commit markers |

`N8N_USER_FOLDER=/data` означает создание `.n8n` внутри `/data`, не размещение всего прямо в `/data`. Для файловых nodes разрешить `/data/work`, сохраняя запрет чтения `.n8n`. Не класть рабочие файлы внутрь защищённого каталога БД ради использования одного volume. Права смонтированного каталога для пользователя node проверить до старта. Источники: [deployment variables](https://docs.n8n.io/hosting/configuration/environment-variables/deployment/), [security variables](https://docs.n8n.io/hosting/configuration/environment-variables/security/).

Прежний `compose.yaml` с двумя томами — кандидат для Docker host. Он не является готовой Railway-конфигурацией и не должен копироваться как её эквивалент.

## Сколько добавится к счёту

Официальные ставки: RAM $10/GB·месяц, CPU $20/vCPU·месяц, volume $0.15/GB·месяц, internet egress $0.05/GB. Минимум Hobby $5 относится ко всему workspace с включённым usage; он не добавляется на каждый service. Если существующий usage уже выше включённой суммы, новые ресурсы в общем случае увеличивают счёт. Источники: [plans](https://docs.railway.com/pricing/plans), [bill](https://docs.railway.com/pricing/understanding-your-bill).

Ниже **условные сценарии**, не замер n8n. Месяц условно 720 часов, диск постоянно содержит 1 GB, CPU указан как среднее использование в часы бодрствования. Трафик, backups и налоги исключены.

| Сценарий | RAM во время работы | Средний CPU | Бодрствует за месяц | Compute + диск |
|---|---:|---:|---:|---:|
| Лёгкий процесс постоянно включён | 0.5 GB | 0.02 vCPU | 720 ч | ≈ $5.55 |
| Более тяжёлый процесс постоянно включён | 1 GB | 0.02 vCPU | 720 ч | ≈ $10.55 |
| Сон, суммарно 2 часа бодрствования в день | 0.5 GB | 0.05 vCPU | 60 ч | ≈ $0.65 |
| Сон, суммарно 30 минут бодрствования в день | 0.5 GB | 0.05 vCPU | 15 ч | ≈ $0.28 |

Формула: `(10 × RAM_GB + 20 × CPU_vCPU) × awake_hours / 720 + 0.15 × stored_GB`. Максимальный лимит CPU/RAM не подставляется как измеренное среднее. Фактический bill считается по времени и меняющемуся использованию. Каждый старт и 5–10 минут ожидания сна входят в awake time. Частые загрузки могут держать процесс включённым весь рабочий день.

Приблизительный egress одного push с 30 MB новых данных — $0.0015, 100 таких push — $0.15; packfile, protocol overhead и иные сетевые вызовы меняют объём. Приходящие в Railway байты — другой поток, не следует считать тариф egress дважды за один исходный комплект.

Следовательно, обещать $0.28 нельзя. До подтверждения сна разумно оценивать **постоянный вариант порядка $5–11+ дополнительного usage/месяц** при допущениях таблицы, после измерений пересчитать. Целевой вариант со сном может быть существенно дешевле.

Лимит расходов Railway уровня workspace отключает **все** его workloads при достижении порога. Нельзя ставить общий hard limit $5 «только для n8n» рядом с Gate. Для n8n использовать измерение service, ограничения RAM/CPU, alerts и отдельное согласование общих лимитов. [Cost control](https://docs.railway.com/pricing/cost-control).

## Конфигурация-кандидат

Это перечень, не применённые настройки:

| Настройка | Предложение | Причина |
|---|---|---|
| Image | Официальный n8n, проверенный exact tag/digest | Готовый движок, воспроизводимость |
| Mode | regular, 1 replica | Без Redis/workers |
| Database | SQLite на persistent volume | Без второго постоянно работающего сервиса |
| Mount | `/data` | БД и рабочие данные переживают restart |
| `N8N_USER_FOLDER` | `/data` | Фактическая БД внутри `/data/.n8n` |
| `N8N_RESTRICT_FILE_ACCESS_TO` | `/data/work` | Ограничить файловые nodes |
| `N8N_DEFAULT_BINARY_DATA_MODE` | `filesystem` | Снизить удержание бинарных данных в RAM |
| `N8N_PAYLOAD_SIZE_MAX` | `64` MiB | С запасом для 30 MB, проверить общий лимит |
| `N8N_FORMDATA_FILE_SIZE_MAX` | `64` MiB | Отдельный file limit multipart |
| `N8N_CONCURRENCY_PRODUCTION_LIMIT` | `1` | Начальная последовательная обработка |
| `N8N_DIAGNOSTICS_ENABLED` | `false` | Уменьшить фоновый трафик |
| `N8N_VERSION_NOTIFICATIONS_ENABLED` | `false` | Проверять обновления при обслуживании |
| `N8N_TEMPLATES_ENABLED` | `false` | Не нужен каталог шаблонов во время работы |
| `WEBHOOK_URL` | Постоянный HTTPS Railway URL | Отдельный платный домен не обязателен |
| `N8N_EDITOR_BASE_URL` | Тот же HTTPS host | Корректные внешние ссылки |
| `N8N_PROXY_HOPS` | Проверить для Railway proxy; кандидат `1` | Корректная схема прокси |
| `N8N_ENCRYPTION_KEY` | Постоянный secret | Сохранять при restart и восстановлении |
| execution data | Не сохранять сырые успешные/ошибочные входы; квитанции отдельно | Не хранить auth headers и 30 MB в каждом execution |
| healthcheck | `/healthz/readiness` | Проверка готовности при deploy; не постоянный внешний polling |
| Serverless | Включить и redeploy; затем доказать sleeping/wake | Не считать toggle доказательством экономии |

В self-hosted Webhook общий payload по умолчанию 16 MiB, а file limit form-data отдельно 200 MiB. Поэтому настраивать и проверять оба, а не считать их одной и той же величиной. У Railway есть отдельные сетевые таймауты: загрузка request body до 5 минут; нельзя гарантировать успешную долгую синхронную обработку без проверки edge timeouts. Если Git долго работает — подтверждение приёма и status endpoint, но успех по-прежнему только после push. Источники: [n8n endpoints](https://docs.n8n.io/hosting/configuration/environment-variables/endpoints/), [Railway networking limits](https://docs.railway.com/networking/public-networking/specs-and-limits).

## Как собрать процесс из готовых компонентов

Основу составляют штатные Webhook → проверка manifest → Read/Write Files → Git Add/Commit/Push → проверка remote → Respond to Webhook. Multipart сохраняет файлы отдельно; JSON manifest содержит имена, относительные пути, размеры, SHA-256 и upload_id. ZIP не нужен; внутренний Git pack не является пользовательским ZIP.

Work готовит manifest и HTTP request программой из локальных файлов, без чтения бинарного содержимого моделью. Вход принимает Header Auth. Не использовать MCP как канал байтов без файлового контракта; для прямого HTTPS MCP не нужен.

Есть существенная работа поверх готовых nodes: валидация путей, журнал upload_id, сериализация, восстановление между commit и push, повтор после потери ответа. Штатные Data Tables умеют хранить и обновлять записи, но это не доказательство атомарной блокировки. Production concurrency=1 не охватывает ручные, CLI и некоторые другие выполнения. Нужны явный единственный writer и тесты аварий. **Не требуется писать собственный HTTP сервер или собственную реализацию Git.** Небольшая детерминированная логика проверки/маршрутизации не заменяет готовые компоненты.

Проверено чтением Git node тега n8n@2.46.6: используется готовая библиотека simple-git; пути Add разделяются запятыми. Поэтому имя с запятой требует отдельного решения, а не слепого объединения имён в строку. Кириллица и пробелы входят в приёмку; ведущие/замыкающие пробелы дополнительно учитывать из-за trim в node. Не обещать поддержку произвольного имени до теста.

Ещё одно найденное место для проверки: credential передаётся в URL для clone/push. Нужно убедиться, что PAT не сохраняется в Git remote config, execution error или process logs; штатное encrypted credential storage само по себе не доказывает отсутствие этих копий. Проверять локально без вывода значения; удалённый URL оставлять без токена. Если штатный путь не обеспечивает этого, выбрать существующий credential-helper подход, не писать новый загрузчик. [Исходник Git node](https://github.com/n8n-io/n8n/blob/n8n%402.46.6/packages/nodes-base/nodes/Git/Git.node.ts).

## Доступ к GitHub

Для первой проверки — fine-grained PAT только для `markmalina/freelance`, Contents read/write, ограниченный срок, хранение в credentials n8n. Для постоянной интеграции с несколькими репозиториями рассмотреть GitHub App с выбранными repository permissions и короткими installation tokens. Существующий ChatGPT GitHub connector не выдаёт n8n свою авторизацию автоматически. Источник: [GitHub token guidance](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens).

Тесты — в отдельной ветке private repo. Доступ к `.github/workflows` и запуск произвольных workflow не предоставлять как побочный эффект файловой загрузки. Push в ветку может запустить уже существующий GitHub Actions workflow; это потенциальный дополнительный расход, который нужно проверить в каждом repository отдельно.

Комплект 30 MB не требует LFS по размеру комплекта. GitHub предупреждает при одном файле >50 MiB и блокирует один файл >100 MiB. Источник: [large files](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github). При росте истории бинарников следить за размером clone.

## Постоянное подключение Work: что удалось выяснить

Из этой обычной Work-среды ранее уже прошёл программный бинарный HTTPS roundtrip. Значит, на стороне отправителя не нужен телефонный download и не нужно гонять Base64 через модель.

В официальной документации OpenAI найден reusable механизм **network secrets и Personal vault для cloud environments**: процессу выдаётся placeholder, HTTPS proxy подставляет secret для разрешённого host на 443. Это подходящий по принципу механизм для webhook token. Но указанная документация описывает **Codex Cloud environments**, а наличие тех же настроек/привязки именно у текущего обычного Work не подтверждено. Источник: [Cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environments).

Нельзя объявлять условие Android/обычного Work выполненным, сославшись на Codex Cloud. Если для каждой загрузки пришлось бы запускать отдельную Codex Cloud задачу, решение нарушит исходное условие. Нужно один раз настроить поддерживаемую привязку к используемой Work-среде и проверить новый обычный Work с телефона. Такой инструмент привязки в текущей сессии не найден.

Если у текущего Work нет постоянной secret binding, остаётся отдельно исследовать поддерживаемый plugin/OAuth канал выдачи короткого upload grant без передачи файлов через MCP. Это возможное направление, **не готовое решение** и не повод сразу писать собственный плагин. Наличие одного только JSON MCP n8n проблему не решает.

## Реальный порядок запуска

1. Получить read-only доступ к действующему Railway: точные workspace/project/environment, текущий bill и ресурсы. Определить путь администрирования n8n, не заимствуя Gate credentials.
2. Подготовить отдельный service и один volume по таблице; оценить дополнительные расходы; согласовать их до создания платных ресурсов. Новый VPS/подписка n8n не нужны.
3. Запустить закреплённый официальный образ; проверить `git --version`, доступность штатных файловых nodes, запись от node в `/data/work`, SQLite и том. Создать owner account до публикации общего входа.
4. Включить Header Auth, HTTPS, secret storage. Пройти уже подготовленный `probe_work.py` на настоящем n8n и повторить из нового обычного Work. Пока этот шаг не проходит, не выдавать готовность цепочки.
5. Настроить Git credential и test branch. Проверить 1 binary: скачать из GitHub, сравнить SHA-256.
6. Собрать batch на готовых узлах. Реально прогнать ~100 смешанных файлов / ~30 MB, Unicode/пробелы, изменения без удаления постороннего, одну commit/push операцию.
7. Ввести сетевой обрыв после принятого push и повторить upload_id. Проверить отсутствие дубликата, конкуренцию комплектов, restart, сохранение pending bytes и receipt.
8. Включить Serverless, redeploy. Закрыть editor и прекратить тестовый трафик, дождаться фактического сна; проверить cold wake и повтор. Снять idle/peak RAM, CPU time, used disk и billed awake time. Отдельно измерить upload, обработку+push, полное время с cold start и без него.
9. Сохранить export без secrets, финальную Railway config и инструкцию повторного использования. Текущий маршрут оставить до принятия нового.

## Что исследовано, а что не выполнено

Подтверждены документацией: модель одного service/volume, SQLite, платформа sleep/wake, тарифы, файловый binary mode, готовые nodes и ограничения. Дополнительно прочитан исходник Git node и официального Docker base тега 2.46.6: base описывает наличие git, но фактический image runtime ещё не проверен.

Не выполнены: создание сервиса, выделение тома, чтение live billing, авторизованный запрос на n8n, Git upload через n8n, испытание сна и замеры потребления. Платные ресурсы не создавались, текущие сервисы и лимиты не менялись.

Практический выбор: **использовать существующий Railway, отдельный маленький service и один volume; начать с SQLite и готовых nodes; включить и доказать сон; постоянный секрет обычного Work оставить отдельной обязательной проверкой.**
