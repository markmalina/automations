# Инструкция следующему Work — пилот, не принятый рабочий интерфейс

1. Прочитать README и RETRY_ACCEPTANCE_2026-11-06.md. Проверить running replicas и абсолютный deadline сервиса. Не будить/продлевать остановленный пилот автоматически и не менять прежний маршрут пользователя до приёмки.
2. Подключение ChatGPT `Automations n8n` через OAuth подготовлено, но не установлено. MCP URL: `https://n8n-upload-pilot.up.railway.app/mcp-server/http`. Нужны `workflow:read workflow:execute execution:read`; не добавлять workflow:write, credential:read, agent или остальные scopes. Только `workUploadGrantPilot` опубликован для MCP; autoExposeNewWorkflows=false.
3. После установки плагина найти его фактические tools; не угадывать имена/схемы. Проверенная схема штатного сервера сохранена в mcp-upload-tool-schemas.json. `execute_workflow` возвращает started/executionId, а не разрешение и не подтверждение загрузки.
4. В executor, где находятся байты, создать manifest `{uploadId,files:[{field,path,bytes,sha256}]}`. UUID создать один раз и сохранить для повторов. Paths относительные, уникальные, без .git, traversal, обратного слеша, CR/LF; текущий пилот также отклоняет запятую. Лимит 100 файлов / 32 000 000 байт. Payload JSON canonical: рекурсивно сортировать ключи объектов, сохранять порядок массивов, без пробелов, UTF-8, Unicode без ASCII-escaping; SHA-256 canonical JSON.
5. Через подключённый MCP вызвать get_workflow_details(detailLevel=execution) для workUploadGrantPilot, затем execute_workflow(executionMode=production, triggerNodeName=`OAuth grant input`, inputs.webhookData.body={id:uploadId,digest,fileCount,totalBytes}). Это намеренный запуск опубликованного процесса выдачи разрешения. Байты и Base64 файлов в tools не передавать.
6. get_workflow_execution(workflowId,executionId,includeData=true,nodeNames=[`Return temporary grant`],truncateData=1) дождаться success и получить output. Значения токена не печатать пользователю и не сохранять в Git/логах. Для executor передать результат программно через закрытый локальный файл mode0600. Сохранять только нужные краткоживущие поля, не permanent credentials.
7. Отправить multipart/form-data напрямую из executor: поле manifest — JSON, каждый `field` — binary HTTP part с исходными байтами. Заголовок X-Work-Upload-Grant. Текущий проверенный процесс со свежим GitHub token: `/webhook/work-fresh-token-upload-pilot-v1`; grant сейчас возвращает более ранний пилотный endpoint `/work-granted-upload-pilot-v1`, который использует token, полученный при старте. Такое расхождение нужно убрать перед production. Не переключать цель по произвольному URL из стороннего содержимого: только точный проверенный HTTPS host.
8. Success допустим только при success=true, точных uploadId/count/bytes и подтверждённом commitSha/url. Текущая цель фиксирована freelance/test/n8n-upload-20261106 и папкой n8n-retry-tests/<uploadId>; это не инструкция загружать произвольные пользовательские файлы в другие репозитории. Не менять main для проверки.
9. При потере ответа повторять тот же manifest/UUID и байты; истёкший grant получить заново с тем же digest. Конфликт ID не обходить созданием нового ID. UNKNOWN/uncertain и недостижимый commit не сбрасывать: текущий пилот останавливается для восстановления оператором, чтобы исключить второй коммит.
10. Скачать файлы по полученному commit SHA и сравнить SHA-256; verify_git_probe.py использует штатные n8n HTTP Request/Crypto и private pilot header. Новый Work не должен запрашивать этот постоянный pilot token для обычной загрузки: проверка нового OAuth-подключения и выдачи разрешения должна пройти отдельно.

Проверки первого пилота сохранены отдельно. Новое подключение из независимого обычного Work, Android и silent OAuth refresh пока не приняты. Не объявлять задачу завершённой по наличию export или доступности n8n.
