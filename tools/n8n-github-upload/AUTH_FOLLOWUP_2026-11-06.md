## Решение-кандидат: постоянный OAuth + краткоживущее разрешение

Долговременную авторизацию хранить в подключении ChatGPT → штатный MCP n8n. Для отправки байтов не пытаться перенести этот OAuth token в shell. Вместо этого перед каждой загрузкой получить ограниченный upload grant через JSON-вызов workflow; затем Work отправляет файлы напрямую по HTTPS с этим grant.

Последовательность:

1. Один раз подключить личный MCP n8n с OAuth в обычном ChatGPT. Проверить предлагаемые scopes; предоставить минимум для исполнения нужного workflow и получения результата, без управления credentials и редактирования workflow там, где это поддерживает выбранная версия.
2. Work вычисляет manifest локально: repository, branch, destination, upload_id, количество, суммарные байты и SHA-256 каждого файла. Байты файлов в MCP не передаются.
3. Через авторизованный MCP запускается небольшой workflow выдачи разрешения на этот manifest. Workflow проверяет allowlist и создаёт случайный short-lived token. Кандидат TTL — 10 минут, лимит — 64 MiB, права — только один комплект в указанное назначение. Это наши проектные параметры, не встроенная функция n8n.
4. Work получает компактный JSON с upload_id, HTTPS endpoint, expires_at и временным token. Секрет не печатать пользователю, не включать в query string и не коммитить. Это ограниченный bearer credential; он также требует защиты.
5. Команда Work открывает готовые локальные файлы и отправляет multipart непосредственно на n8n с token в заголовке. Содержимое файлов не проходит через модель.
6. n8n проверяет срок, manifest binding, размеры, хеши и состояние операции; после Git push возвращает квитанцию. Повтор того же upload_id проверяет результат и не получает право на другой комплект. Одно разрешение относится к одному комплекту, а не обязательно к одной сетевой попытке.

Таким образом, не требуется постоянный N8N_UPLOAD_TOKEN в каждом executor и не требуется отдельная задача Codex Cloud для каждой загрузки. Но это ожидаемое свойство предлагаемой архитектуры: его ещё нужно доказать в новом обычном Work и с Android.

## Что подтверждено первичными источниками

Штатный instance-level MCP n8n поддерживает OAuth и инструкции для ChatGPT. Авторизация проводится один раз как подключение клиента; n8n позволяет выбирать выставленные workflow и просматривать выданные права. [Документация](https://docs.n8n.io/connect/connect-to-n8n-mcp-server/).

Документированный `execute_workflow` принимает JSON, возвращает executionId; результат читается отдельно через `get_workflow_execution` с includeData. Следовательно, нельзя считать ответ status=started уже выданным разрешением. Для первого grant-workflow нужно проверить доступность возвращаемого JSON и настройки сохранения execution data. Не переносить настройки «не сохранять ничего» с binary workflow слепо на workflow выдачи разрешения, если результат читается из execution data. Временно сохранённый bearer token имеет узкую область и срок, но его копии в executions всё равно нужно ограничивать и удалять по политике. [Tools reference](https://docs.n8n.io/connect/connect-to-n8n-mcp-server/mcp-server-tools-reference).

Генерация случайной строки и SHA-256 имеются в штатном Crypto node, операции хранения/поиска — в Data Tables. Binding, replay и атомарность не появляются автоматически: нужна небольшая детерминированная логика и аварийные тесты. Новая реализация OAuth, MCP transport, HTTP multipart parser или Git с нуля не требуется.

Схема tools/list действующего n8n не получена — экземпляр пока отсутствует. Прочитана опубликованная схема инструмента, а не live ответ. В актуальных docs есть функции n8n 2.47.0; их нельзя считать доступными в ранее выбранном 2.46.6. После запуска закрепить реально проверенную версию и схему.

## Почему JSON MCP теперь полезен

Ранее было установлено, что JSON MCP не доказывает передачу файлов. Этот вывод сохраняется. Здесь MCP используется только для команды авторизации, а не файлов. Байты по-прежнему идут Work → HTTPS Webhook n8n. Отсутствие openai/fileParams на данном управляющем инструменте не блокирует этот вариант.

## Остаток по Railway и минимальное действие владельца

Фактическое отсутствие подключения установлено инструментом и интерфейсом. Сейчас я не могу прочитать live проекты/usage или развернуть n8n от имени аккаунта через Railway plugin.

Минимальное действие: установить Railway из открытой карточки и завершить авторизацию нужного существующего аккаунта. Не присылать API token в чат. Это отдельное разрешение на подключение аккаунта, а не согласие на новые расходы. После подключения сначала проверить доступные инструменты и выполнить read-only осмотр. Не запускать платного Railway Agent/новые ресурсы без необходимости и согласованного бюджета. Если действующий Ops требует собственный requester для выбранного target, подготовить этот канал, не обходя его credentials других проектов.

Для n8n OAuth позднее также потребуется однократное подтверждение подключения владельцем, когда уже будет HTTPS URL. Пока URL нет, пустую форму не отправлять.

## Обязательная живая проверка перед объявлением решения

1. Получить `tools/list` именно подключённого n8n, проверить input/output и минимальные OAuth scopes.
2. Выполнить grant-workflow, получить его конечный JSON, передать файл из текущего Work, сравнить SHA-256.
3. Проверить истёкший grant, другой manifest, другой repo/branch, превышение bytes/count, повтор после потери ответа и restart.
4. Повторить из нового обычного Work с той же OAuth connection, без ручного секрета/отдельного Codex Cloud task; затем с Android.
5. После этого провести всю исходную пакетную приёмку. До неё текущий способ загрузки действует.
