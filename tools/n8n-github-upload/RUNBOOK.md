# Настройка и следующий Work

Это инструкция для продолжения, а не подтверждение работающего подключения.

## Первая контрольная точка

1. Выбрать существующий разрешённый сервер или точный deployment target. Проверить доступ, текущие расходы и запас ресурсов. Не использовать credentials Gate для n8n.
2. На разрешённом Docker host скопировать конфигурацию, заполнить `.env` вне Git с правами 0600. Сгенерировать постоянный случайный N8N_ENCRYPTION_KEY средствами secret manager; сохранить резервную копию ключа отдельно от БД. Выполнить `docker compose build`, проверить успешный `git --version` и создание каталога под пользователем node.
3. Подключить существующий reverse proxy с действительным TLS к `127.0.0.1:5678`, body limit не менее 64 MB, подходящими таймаутами. Точное имя хоста и конфигурация TLS пока не определены. Не публиковать порт 5678 напрямую.
4. Запустить n8n, создать owner account. Импортировать `probe.workflow.json` без публикации. Создать штатный Header Auth credential: имя заголовка `X-Work-Upload-Token`, значение — случайный секрет. Привязать credential к Webhook и только затем опубликовать workflow.
5. В Work через доступную защищённую настройку окружения привязать `N8N_UPLOAD_PROBE_URL` и `N8N_UPLOAD_TOKEN`. Секрет не вставлять в чат, командную строку, URL, логи или Git. Инструмент привязки секрета к текущей среде Work сейчас не найден; этот шаг остаётся отдельным условием, а не решённой настройкой.
6. Из обычного Work выполнить `python probe_work.py`. Получить HTTP 200, совпадение SHA-256 и 4096 байтов. Сохранить только JSON-квитанцию без секретов. Повторить из новой Work-среды, управляемой из Android: наличие инструкции само по себе не переносит секрет.
7. Запрос без заголовка и с неправильным секретом обязан завершаться отказом. Проверить, что сохранённые executions/logs не содержат заголовка авторизации. Настройки отключения execution data в compose нужно проверить на выбранной версии, включая ограничения платформы логирования.

## После первой проверки

Переходить к реализации `DESIGN.md`, сохраняя штатные Webhook, Read/Write Files и Git nodes. Не писать собственный HTTP загрузчик или backend, пока не доказано отсутствие необходимой возможности в штатных компонентах. Сейчас такой вывод не делался.

GitHub доступ n8n: выделенный fine-grained PAT с Contents read/write только для разрешённых репозиториев либо GitHub App с соответствующими установками. Секрет в n8n credentials; не в clone URL/export. Work не получает GitHub token. Для первоначальной проверки достаточно private `markmalina/freelance` и отдельной test branch. Другие репозитории требуют явного включения в список доступа.

## Перезапуск и потеря диска

В compose БД n8n, credential storage и настройки лежат в volume `n8n_data` (`/home/node/.n8n`). Будущие рабочие копии Git, загрузки и журнал — в `upload_data` (`/home/node/.n8n-files`). После перезапуска с теми же томами они сохраняются; это ещё нужно проверить реально.

Git clone можно восстановить из GitHub после потери рабочей копии, но клон не восстанавливает непереданные байты и журнал незавершённых комплектов. Для них нужен backup `upload_data`. При потере журнала сначала восстановить его, затем проверить remote commit markers; нельзя автоматически повторно коммитить неизвестную операцию. Для восстановления n8n требуются backup БД и тот же encryption key.

Для Railway эти mount paths и DB/ledger должны оказаться на persistent volume; compose сам по себе этого не настраивает. Railway-specific конфигурация сознательно не выдана за готовую без выбранного project/service/volume.
