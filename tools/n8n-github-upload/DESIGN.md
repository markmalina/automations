# Будущий процесс: требования к реализации

**DESIGN ONLY. Production workflow ещё не реализован.**

## Транспорт

Для первой проверки — raw `application/octet-stream`, один синтетический файл и бинарный ответ. Для комплекта кандидат — multipart/form-data с JSON manifest отдельным текстовым полем и файлами под ключами `file000`…`file099`. Manifest сопоставляет каждый ключ с относительным UTF-8 путём, длиной и SHA-256; путь не извлекается из multipart filename. Это позволяет сохранить вложенные каталоги, пробелы и кириллицу без ZIP и без Base64 через модель. Реальный multipart mapping нужно проверить на выбранной версии n8n.

Штатный Webhook по умолчанию ограничен 16 MB; на self-hosted задать 64 MB и проверить reverse proxy и отдельный multipart/form-data лимит текущей версии. При недостаточном лимите — staged uploads под одним upload_id, затем finalize. Это решение пока не принято: выбирать после живой проверки.

## Контракт manifest

Поля: `version`, случайный `upload_id`, `repository`, `branch`, `destination`, `message`, `files[{field,path,size,sha256}]`. Сервер хранит digest канонического manifest вместе с репозиторием, веткой и назначением. Секрет не входит в manifest. Один upload_id с другими параметрами даёт конфликт.

Репозитории и допустимые ветки задаются серверным allowlist; произвольные clone URL не принимаются. Запретить абсолютные пути, `..`, `.git` на любом уровне, NUL, backslash, симлинки и выход из корня; отклонить повторяющиеся пути и небезопасные префиксы file/dir. Пользовательские строки не подставлять в shell. Проверять число, размеры и каждый digest до изменения рабочей копии.

## Штатные узлы и состояние

Webhook Header Auth → проверка manifest → отдельная staging-папка upload_id → Read/Write Files → серверная сериализация для пары repo/branch → Git Fetch/Clone/Switch → перенос только заявленных файлов → Git Add заявленных путей → Git Commit один раз → Git Push один раз → независимое чтение remote ref → квитанция.

Валидация, блокировка и durable idempotency ещё требуют проектирования. N8N concurrency=1 само по себе не является блокировкой между процессами и не решает crash recovery. Не выдавать набор независимых Git nodes за транзакционный процесс. Перед решением с собственным кодом проверить штатные Data Tables/БД transactions и существующие компоненты.

Состояния: RECEIVED → VALIDATED → STAGED → COMMITTED(sha) → PUSH_CONFIRMED(receipt). Журнал должен быть постоянным и атомарно связывать upload_id и manifest digest. Commit message должен содержать серверный marker upload_id + manifest digest, чтобы восстановить связь при аварии между созданием commit и записью журнала.

Повтор PUSH_CONFIRMED возвращает ту же квитанцию. После неизвестного результата push сначала fetch и проверка удалённой истории: если commit с marker и ожидаемым manifest существует — не коммитить и не push повторно. Если локальный commit создан, а push не прошёл, использовать тот же commit. На non-fast-forward вернуть конфликт; не force-push и не делать скрытый второй commit. Потеря ответа не доказывает неуспех push.

Другая задача получает отдельную staging-папку; Git worktree/clone и блокировка исключают смешивание. `git add -A` по всему репозиторию и удаления не допускаются. Пустое обновление возвращает NO_CHANGE с проверенным существующим SHA; поведение отдельно проверить.

## Результат и замеры

Успех только после проверки remote SHA (или достижимости принятого commit при согласованной модели конкуренции). Ответ: repository, branch, commit_sha, GitHub commit URL, file_count, total_bytes, upload_id, manifest digest. Не включать секреты и бинарные данные.

Измерять клиентом время передачи последнего байта в n8n, сервером — приём/валидацию/запись и Git push, клиентом — общее время до подтверждения. Длительность roundtrip диагностического echo не выдавать за длительность загрузки в GitHub. На успешном номинальном пути подтвердить одну операцию commit и одну push; retry может выполнять повторную проверку remote, не новый commit.
