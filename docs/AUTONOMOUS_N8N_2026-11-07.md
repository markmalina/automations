## Цель и оценка решения

Обычный свежий Work сам готовит файлы, получает короткий grant через прежний OAuth, посылает binary multipart в n8n и возвращает commit URL после независимой проверки bytes по exact SHA. Любой назначенный владельцем repo markmalina, включая private, в рамках реальных прав App/ветки. Секреты/байты не проходят через модель. Создание веток/PR и workflow files — по S5/соответствующим правам, а не обещание неограниченной записи.

n8n подходит как выбранный сервис: исходники/локальные native import/publish/grant и readback уже прошли ограниченные проверки. Не доказана его принципиальная непригодность. Отказ конкретного Railway Deploy не является доказательством дефекта n8n. Если обнаружена непреодолимая техническая несовместимость, контроллер немедленно сообщает конкретный критерий и доказательство; платформа/тариф/новый сервис самостоятельно не заменяются.

Приняты: №10/S2.A verifier+bridge, №12/S2.B малый private readback, №13/S1.N локальный native check. S1/№9 остаётся BLOCKED. Native readiness ещё не гарантирует ожидаемый snapshot. Все новые циклы читают свежие receipts, не повторяют эти приёмки без новой причины.

## Очередь и роли

Контроллер читает последние comments координационной issue, активную task, current main/PR/CI и состояние предыдущего исполнения. В одном месте оставляет текущие TASK_URL,QUEUE_STATE (READY/RUNNING/REVIEW/WAITING_EXTERNAL/DONE),source/head и последнее решение.
Исполнитель берёт только явно READY задачу; до записи проверяет claim/PR/jobs, пишет execution ID/source/ветку и RUNNING. Один outcome — один writer. Истечение времени claim не доказывает завершение: при неизвестном эффекте только чтение/reconcile, не второй writer. Не строить отдельную систему leases.
После результата worker сохраняет код/один необходимый CI/receipt, проверяет remote readback, пишет REVIEW и заканчивает. Issue/PR остаются до решения контроллера. Следующий worker не пересоздаёт этот результат.
Контроллер проверяет реальный diff/hashes/тесты по масштабу; принимает и может merge допустимый source PR в Automations, закрывает завершённую task, назначает следующую. Если defect — одно конкретное исправление в той же task/PR. Серверный candidate S1 меняется только отдельным принятым source diff, не самовольно.
Все назначения содержат прямой WORK-RULES URL. Марк не должен просыпаться ради обычных обратимых технических решений. Другие проекты и их автоматизации не изменять.

## Приоритеты адаптивного плана

1. В каждом controller цикле проверить только новые ответы в case19384733 (существующая Gmail цепочка) и material GitHub progress. Разрешены фактические ответы на конкретные вопросы поддержки в том же обращении, без секретов/спама/расширения аудитории. Не писать повторные «поторопитесь» каждый час.
2. При доказанном исправлении причины/применимом допуске исходного Deploy — следующий приоритет продолжить №9 по обновлённым критериям, подготовить exact candidate/pending и пройти штатный механизм. Исходный отказ не повторять ради диагностики и не обходить эквивалентным UI/CLI/Ops effect. Письмо «изучаем», новое общее разрешение или истечение времени сами по себе не снимают блокер.
3. При отсутствии допуска — сначала реальный Work data path: стандартные proxy/CA/TLS, существующий клиент, без ручного переноса secret. Первый подготовленный ограниченный outcome — supported proxy path клиента. После него — конкретная native binary execution/integration на synthetic fixture и минимальном локальном GitHub stub, если это действительно закрывает непроверенную часть; не строить framework и не выдавать stub за real GitHub.
4. Параллельно без writer конфликтов можно уточнять штатную read-only диагностику admission/effective permissions и собирать запрошенное поддержкой. Не менять permissions/full_access/credentials/сервисы/подписки по догадке.
5. Если S1 установлен — сразу полезный S2: один Unicode+binary комплект в выделенные тестовые paths Automations и по разрешённому текущему scope Freelance (служебная ветка; не затрагивать ArtOx). Создавать/обновлять только synthetic fixtures, с точным manifest/пределами и независимым readback, затем update/replay с тем же UUID. Private write/live scope проверять отдельно, не выдавать read-only №12 за n8n App permission.
6. Затем исходный S3:100файлов/30,000,000bytes,3цикла, отрицательные случаи/ресурсы. Потом S4 recovery/status и S5 destinations/PR; S6 freshness/restart/refresh по реально доступному времени. Не утверждать суточный uptime за восьмичасовое окно.
7. Если все оставшиеся действия требуют неразрешённого внешнего эффекта — сохранить конкретный WAITING_EXTERNAL, готовый пакет продолжения, проверить новые сведения в следующий цикл. Не производить фиктивный прогресс, новые audits/issues/CI вокруг неизменного blocker. Каждый отчёт честно сообщает пользовательский результат.
