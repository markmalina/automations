## Пользовательский результат и граница

**FAIL на первом native binary запросе, HTTP500 / E_MANIFEST.**
n8n2.46.6 действительно выполнил бинарный webhook на двух малых synthetic файлах,
но до GitHub stub writes не дошёл. Receipt/replay/remote bytes не подтверждены.
Реальных n8n/GitHub/Railway операций не было; production source не исправлялся.

Установленный parser gap: client multipart manifest part содержит
`Content-Type: application/json`. Установленный настоящий n8n multipart parser
классифицирует такую часть как файл. В текстовом body нет manifest, тогда как
первый валидатор Prepare upload требует string body.manifest и выдаёт E_MANIFEST.
Первый node локализован по native log/VM source stack и отдельному parser
reproducer, а не по недоступному полному runData.

## Воспроизведение и ограничения harness

Добавлены только два test-only probes и этот отчёт. Нужны isolated n8n2.46.6,
рабочий SQLite и own0700 root с node_modules и source directory, содержащей exact
work_upload.py/upload-ledger.cjs/owner-repository-upload.workflow.json.
Скопировать probes в эту own root, затем:

```sh
python native_binary_probe.py --root "$task_dir"
node multipart_parser_probe.cjs "$task_dir"
```

Первый script сам готовит fresh private runtime, fake owner/JWT, loopback stub,
native published snapshot, один upload и только при успехе replay. Читает
безопасные execution metadata и останавливает свои n8n/stub процессы finally.
Runtime/keys/DB/logs оставлены им приватно для read-only диагностики, их обязан
удалить оператор после сохранения безопасного результата. В этом Work они удаляются
до terminal receipt. Итог смотреть в outcome/phase/errorCode, а не в одном exit0
сборщика metadata. Stub tree/commit IDs синтетические; только blob SHA реально
пересчитывается по Git object bytes. Нет real GitHub readback.

Разрешённый local export diff:
- /nodes/1/parameters/jsCode: только GitHub origin →loopback;
- /nodes/8/parameters/command, /nodes/27/parameters/command,
  /nodes/33/parameters/command: только ledger absolute path;
- /nodes/10/credentials/jwtAuth/name: только имя fake credential;
- /nodes/11/parameters/url: только installation endpoint origin→loopback.
Graph, binary/hash/claim/receipt logic не менялись.

Первый harness остановился до binary на AttributeError: функция http затеняла
import http.client. После локального исправления snapshot check заметил ровно
jwtAuth.name normalization. Имя явно согласовано с fake credential, создана свежая
DB; только затем выполнен один binary POST. Эти helper failures не являются
отказами production source и не скрыты. Ни один из них не вызвал binary повтор.

**Ограничение диагностики:** после stop подробная execution_data недоступна
SQLITE_CORRUPT; execution_entity id/status/workflowVersionId читаются. Причина
повреждения/недоступности payload table здесь не устанавливалась и не приписывается
production. Полные runData/lastNode из DB не получены. Последний metadata extractor
в опубликованном harness использует реальный execution_entity.workflowVersionId
и отдельно обрабатывает недоступный payload; прежний helper ошибочно искал
versionId в workflowData. Direct metadata query проверена на фактической БД.
Повторять binary failure ради extractor не стали. Parser reproducer от SQLite
не зависит и отдельно подтверждает установленную MIME-классификацию.

Локально: py_compile, node --check, настоящий native error и parser reproducer.
Hosted source CI проверяет baseline tests/syntax, а не этот внешний native scenario.
Его состояние и exact head фиксируются в terminal receipt, не подменяют FAIL.
