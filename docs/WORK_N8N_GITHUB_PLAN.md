## 1. Пользовательский результат

Марк в обычном новом Work поручает сохранить подготовленные или приложенные файлы в конкретный свой репозиторий GitHub. Исполнитель определяет файлы и назначение, получает краткосрочное разрешение через уже установленное подключение n8n, программно передаёт байты, проверяет результат на GitHub и возвращает ссылку на коммит; для защищённой ветки — также на PR.

От Марка при штатной выгрузке не требуется создавать токены, переносить секреты, редактировать workflow, запускать локальный компьютер, нажимать Railway Deploy, открывать другой Work или выполнять команды. Репозиторий и каталог можно брать из уже назначенного контекста; существенное неоднозначное назначение нельзя угадывать.

«Любой Work» проверяется как новая сессия поддерживаемого Work Марка с доступом к исходным файлам, установленному подключению и разрешённой передачей файлов. Подключённый MCP сам по себе не даёт shell доступ в интернет. Задача включает устранение препятствия в реальных средах Марка; нельзя обещать обход ограничений платформы или чтение файлов из недоступного чужого Work.

Начальная приёмочная нагрузка: 100 отдельных файлов / 30 000 000 байт. Файлы появляются отдельными путями в Git, с кириллицей, пробелами и вложенными каталогами; один опубликованный коммит на комплект. В исходнике сейчас установлен предел 32 000 000 байт и 100 файлов. Больший объём требует явно другой приёмки; дробление не выдаётся за один коммит всего исходного комплекта.

Завершение — это доказанная цепочка из нового Work, а не PR, зелёный CI, работающий редактор n8n или подготовленный отчёт.

## 4. Предлагаемая схема и решения

### 4.1. Оставить одну простую схему

| Компонент | Ответственность |
| --- | --- |
| Work | Найти файлы, определить repo/branch/path, вычислить manifest, передать байты, проверить GitHub и показать результат. |
| Существующий OAuth/MCP n8n | Одно подключение аккаунта; короткое разрешение на конкретный комплект. По этому каналу идут метаданные. |
| HTTPS upload workflow n8n | Проверить grant, размеры, хеши и назначение; сохранить комплект Git Data API; выдать проверенную квитанцию. |
| SQLite на существующем /data | Привязка uploadId к manifest/target, состояние исполнения и подтверждённый commit; сведения переживают рестарт. |
| Существующий GitHub App | Серверная авторизация; короткий installation token ограничивается нужным репозиторием. |
| Railway / Ops | Установка и обслуживание сервиса. В штатной передаче каждого комплекта не участвуют. |

Оставить один сервис, SQLite и существующий диск. Не добавлять PostgreSQL, Redis, отдельный upload server, object storage, вторую подписку, дополнительную LLM или Railway Agent без доказанной необходимости.

Передача Work → n8n остаётся бинарным HTTPS multipart. Внутренняя кодировка Base64 для GitHub blob API допустима и не выводится в модель. Ни ZIP, ни ручное кодирование содержимого не входят в пользовательский сценарий.

### 4.2. Изменить порядок, не переделывать готовое

1. Основной первичный запуск — исходный штатный Railway Deploy после действительного разрешения его отказа собственным механизмом допуска. Общая фраза «делай» уже не доказала устранение причины; бесконечные повторы не планируются.
2. Не заменять этот отклонённый эффект эквивалентной записью через другой интерфейс. Ops не является способом спрятать или обойти отказ.
3. Полную доводку Ops #434 убрать из критического пути первого upload. Сохранить прежнее предпочтение Ops для последующего обслуживания; если этот маршрут будет принят, выполнять его отдельные reviewed contracts, не просто enabled=true.
4. Один согласованный release на основе PR #8: точные bootstrap/ledger/workflows, exact hashes, persistent mode, ограниченная уборка старых подтверждённых временных данных, сохранение журналов. Никакого повторного написания клиентской и grant-логики с нуля.
5. Объединение плановых частей в этом документе не отменяет правил защищённых инфраструктурных операций, независимой проверки или точного подтверждения дельты, если соответствующий механизм их требует.
6. Не ставить открытие репозитория, полную уборку истории PR и создание универсальной платформы развёртываний впереди первого работающего сохранения файлов.

### 4.3. Границы текущего кандидата

Основные имена сохраняются: workUploadGrantPilot, workOwnerRepositoryUploadV1, существующее OAuth-подключение и GitHub App. Подключение нового постоянного секрета на каждый Work исключено.

Новая запись поддерживает добавление и обновление; удаление чужих файлов не входит в задачу. Не отключать branch protection и не использовать force push. Репозитории организаций не считать покрытыми установкой App на личный markmalina: при реальной необходимости отдельно проверить installation и права.

Git LFS, submodules, произвольные чужие репозитории и неограниченный размер пакета не являются подтверждёнными возможностями. Наличие файла с необычным Git mode не должно приводить к молчаливому повреждению его типа.

## 5. Спринты до результата

Это последовательные этапы одного исполнения, а не требование шести новых Work или шести команд «продолжай». В текущем поручении они только спланированы.

### Спринт 1. Один согласованный release и работающий постоянный сервис

**Результат:** установлен именно проверенный универсальный исходник, процесс работает после прежнего deadline, grant workflow доступен.

Задачи:
1. Перед реализацией перечитать актуальные main, pending patch и остаток чужой активности; закрепить один исполняемый source SHA. Документальный коммит с этим планом не считается новой версией runtime.
2. Сопоставить PR #8 и старые #3/#5: восстановление диска и наблюдение уже присутствуют в новой основе. Включать только действительно недостающую дельту.
3. Подготовить ровно один patch нового source и настроек на фиксированный target; учесть чужие pending changes. Проверить согласованность двух исходников, workflow exports, startup/import/publish, image и restart policy.
4. Сохранить безопасный baseline журнала и failed upload ID 9d94bcf3-9a28-4014-93d5-ce8e5d259c7d. Подготовить проверяемый возврат кода, совместимый с уже изменённой схемой; не сбрасывать volume или БД.
5. Разобрать прежний отказ исходного Deploy. Проверить доступный штатный путь явного допуска и доступные безопасные признаки ошибки. Повторять исходную операцию только при факте устранения причины/появлении действующего допуска. При непреодолимом отказе — точный внешний blocker с готовой дельтой.
6. После разрешённой установки: terminal deployment SUCCESS, running=1, /healthz и readiness, установленные hashes, фактический persistent mode, свободные bytes на диске, успешный native import/publish двух workflow.
7. Проверить доступность grant workflow через существующее OAuth/MCP. Не считать импорт JSON доказательством его исполнения.

**Приёмка:** 1/1 правильный deployment; 1/1 работающий процесс; 2/2 workflow импортированы/опубликованы; старые journal/failed ID сохранены; процесс не остановился из-за истёкшего пилотного deadline.

**Первый стоп:** непройденный механизм допуска. В этом случае продуктовый запуск не объявлять сделанным, не писать очередной большой control framework вместо разрешения конкретного отказа.

### Спринт 2. Обычный Work действительно сохраняет файл

**Результат:** первый полезный пользовательский маршрут; один файл и обновление проходят в два разных репозитория, включая приватный.

Задачи:
1. Сделать короткую проверку среды Work: файлы доступны, Python/shell имеются, подключение находится, разрешён HTTPS до нужного n8n. Настройки интернета и состояние сервера диагностировать отдельно.
2. Если нужен proxy, приспособить клиент к поддержанному proxy/TLS пути среды. Не отключать TLS и не использовать сетевой обход.
3. Упаковать уже готовый prepare → grant → upload → verify в повторно используемую инструкцию и helper. Получение и сохранение короткого grant выполняются программно, без его появления в модели, argv или stdout.
4. Получать helper из закреплённой проверяемой версии. Не заставлять пользователя скачивать его, создавать bundle/grant-файлы или копировать команды.
5. Автоматизировать независимый GitHub readback по exact commit: программно получить реальные bytes, проверить размер и SHA-256. Ограничения коннектора для бинарных ответов проверить на реальном файле; Base64 не выводить в модель.
6. Проверить бинарный файл и текст с Unicode; обновить один существующий файл; повторить тот же uploadId. Проверить второй репозиторий, чтобы не воспроизвести старое ограничение Freelance.
7. Обновить опубликованное описание инструмента: оно больше не должно обещать только Freelance. Существующий OAuth остаётся.

**Приёмка:** минимум 2/2 репозитория, 1/1 обновление только нужного пути, 1/1 replay с тем же SHA, все проверенные байты совпали. В ответе — ссылка на коммит. Ни одного нового постоянного токена и ручного Deploy для этих upload.

После S2 уже есть полезная работающая функция. Полная приёмка задачи ещё впереди.

### Спринт 3. Пакет 100 файлов / 30 МБ и ресурсы

**Результат:** основная массовая выгрузка проходит без переполнения памяти/диска и без зависимости от истории репозитория.

Задачи:
1. Один воспроизводимый смешанный комплект: бинарные и текстовые данные, вложенные пути, пробелы, кириллица, реальные форматы документов. Не использовать личные данные Money/Energy или рабочий Gate/AQUB как тестовые фикстуры.
2. Отправить 100 файлов / ровно 30 000 000 байт. Один опубликованный commit, один родитель; все 100 файлов скачать из exact SHA и проверить.
3. Проверить обновление части пакета и сохранность посторонних путей. Размер истории исходного repo не должен вызывать clone.
4. Согласовать лимиты на клиенте, ingress, multipart parser и n8n, включая накладные расходы HTTP. Проверить 101 файл, превышение суммарного размера, неверный hash и неполный multipart.
5. Измерить полное время, обработку, ожидание очереди, память, свободный диск и объём временных данных. Существующее ограничение write-потока 1 запрос/сек означает больше 100 секунд только на blobs; старые 24–38 s не обещать для новой архитектуры.
6. Согласовать очередь, client timeout и execution timeout с запасом; одинаковые 300 s на сервере и клиенте сами по себе не обеспечивают запас на очередь и сеть. Выдавать понятный busy/retry-after вместо неограниченного ожидания.
7. Проверить native binary pruning после успеха и ошибки. Выключенное сохранение execution payload не считается доказательством очистки файлов.
8. Проверить несколько последовательных пакетов, как минимум три полных цикла. Для проверки RAM/pruning допустимо повторно использовать те же binary blobs в выделенной тестовой области, не накапливая ненужные сотни мегабайт в Git.
9. Предварительные целевые пороги: RAM peak до 80% текущего лимита и свободный диск перед полным пакетом не меньше 256 MB. Это проектные пороги с запасом, не измеренные факты. Если новая версия их не выполняет — исправить либо обосновать другой порог до приёмки; не увеличивать ресурсы молча.

**Приёмка:** 100/100 SHA-256; 1/1 опубликованный commit; нет изменений вне manifest; минимум 3/3 последовательных цикла без неограниченного роста; негативные случаи не меняют целевую ветку.

### Спринт 4. Проверка состояния и восстановление после сбоя

**Результат:** обычные обрывы не требуют нового токена, нового uploadId, второго опубликованного коммита или ручного редактирования SQLite.

Задачи:
1. Добавить в общий клиент и server contract ограниченные status/reconcile/resume для своих uploadId. Доступ к чужим данным не открывать.
2. Сохранять точные фазы: комплект принят, разрешение проверено, операция занята, подготовлен/создан commit, публикация отправлена, remote подтверждён. Журналировать перед внешними эффектами там, где это необходимо для восстановления.
3. Потеря ответа после успешного ref update: прочитать состояние GitHub, подтвердить прежний commit и вернуть его.
4. Commit записан, ref не обновлён: проверить прежний parent, текущее состояние ветки, содержимое и отсутствие уже выполненного эффекта; завершить допустимую публикацию того же commit. При конфликте вернуть конфликт, а не делать force.
5. Обрыв до записи SHA или неизвестный ответ GitHub: восстановить по заранее сохранённым проверяемым данным; если доказательств недостаточно, остановиться с точной причиной. Нельзя обещать exactly-once произвольного API-вызова без такого доказательства.
6. Определить безопасную передачу владения незавершённой операцией после смерти execution; не сбрасывать claimed только по истечению времени.
7. Два одинаковых параллельных запроса должны дать один опубликованный commit и тот же receipt. Два разных комплекта в одну ветку не должны терять изменения; пересекающиеся правки дают явный конфликт.
8. Проверить истечение grant и App token, потерю ответа, restart в существенных фазах и replay после продвижения ветки.
9. Сохранить прежний failed ID и выяснить доступность его исходного manifest/байтов. Если исходные bytes утрачены, не подставлять другой комплект под тот же ID и не выдавать выдуманный восстановленный результат.
10. Структурировать ошибки: отказ авторизации, неверные данные, конфликт, busy, исчерпание ресурсов и неизвестный исход. Не ограничиваться HTTP 500 без безопасного error code.

**Приёмка:** все предусмотренные окна сбоя имеют проверенный исход — подтверждённое восстановление либо обоснованный безопасный отказ; в успешных восстановлениях 0 лишних опубликованных коммитов. Рестарт сохраняет журнал и исходные привязки.

### Спринт 5. Назначения и правила репозитория

**Результат:** маршрут пригоден для реальных репозиториев Марка, включая защищённые ветки, а не только для заранее созданной тестовой ветки.

Задачи:
1. По метаданным определить реальную default branch; не предполагать везде main. Проверять immutable repo ID и владельца.
2. Сохранить прямую запись туда, где она разрешена поручением и GitHub.
3. Где требуется PR — создать рабочую ветку от актуальной базы, сохранить комплект в неё и открыть PR. Новый upload сохраняет один data commit; создание PR не должно вызывать повторную загрузку.
4. Проверить, нужны ли App permissions Pull requests:write. Для записи .github/workflows — отдельно Workflows:write. При реальной необходимости расширить существующий App ровно этими правами; не создавать новый PAT или private key. Если право не получено, прямо назвать непокрытый случай.
5. Проверить сохранение режима существующих обычных/исполняемых файлов, отсутствие молчаливой замены symlink/submodule другим типом. Не добавлять отдельную поддержку submodules без потребности.
6. Проверить необычные допустимые имена: нынешний запрет запятой и приведение только к NFC не считать универсальной поддержкой имён. Устранить лишнее ограничение либо явно описать точный остаток.
7. Пустой существующий repo обнаруживать отдельно: изучить допустимый initial-commit путь с одним итоговым data commit. Не создавать новый репозиторий только ради этой задачи без отдельной необходимости. Если этот случай не реализован, не скрывать его за обещанием «любой repo».
8. Убедиться, что новые коммиты App вызывают нужные проверки целевого проекта и не запускают непредусмотренное развёртывание при тестировании.
9. Не менять приватность целевых репозиториев и не отключать их защиту.

**Приёмка:** матрица public/private, default branch, существующая произвольная ветка и protected branch/PR пройдена. Дополнительные права и оставшиеся ограничения обозначены фактически; доступ за пределы выбранного repo не выдан короткому token.

### Спринт 6. Новый Work, длительная работа и обслуживание

**Результат:** готовый повседневный способ работы с понятной эксплуатацией.

Задачи:
1. Закрепить инструкцию и helper в существующем подключении/пакете инструкций, обновить root README/точку входа. Не рассчитывать, что новый Work помнит предыдущий чат.
2. Проверить минимум две действительно новые сессии Work, одна с Android и одна с web/desktop, когда доступна соответствующая среда. Внутренний subagent не выдаётся за новый независимый Work. Тест не требует от Марка переносить секреты или повторять установку.
3. Проверить OAuth refresh после фактического истечения access token, а не только новый 10-минутный grant. Проверить upload после срока прежнего GitHub installation token.
4. Провести ограниченное суточное наблюдение постоянного процесса: работа после idle, новые файлы, диск/память, сохранность журнала. Это будущее испытание после разрешённого запуска, не созданная сейчас автоматизация.
5. Проверить одно обслуживающее обновление и возврат совместимого кода без потери OAuth, encryption key, журнала и квитанций. Сохранить резервную копию через разрешённый механизм; не выгружать БД с секретами в публичный Git.
6. Для желаемого обслуживания через Ops завершить только узкий n8n-контракт в Ops #434: принять нужные source/patch/bindings, штатный requester/control/observer и native API interaction. Существующий рабочий read route не переписывать. Механически объединять весь старый draft не требуется.
7. Если полная интеграция Ops остаётся отдельной незавершённой задачей, рабочую выгрузку принять по её собственным фактам, а Ops явно оставить открытым. Не называть Ops готовым и не делать его участником каждого upload.
8. Зафиксировать версию клиента/runtime, таблицу поддерживаемых случаев, ресурсные лимиты, место журнала и способ диагностики. Старые PR пометить как замещённые только после сверки и сохранения полезных частей.
9. В Automations #1 привести checklist в соответствие фактической приёмке. Не закрывать всю задачу по зелёному CI.

**Приёмка:** 2/2 новые сессии, silent refresh проверен, upload после idle/restart/update прошёл, первый суточный интервал наблюдения завершён без необъяснённых остановок и роста данных. Нулевой перенос постоянных секретов между Work. У статуса Ops отдельное честное значение.

## 6. Отдельный этап P: открыть Automations и сократить расходы CI

Предложение Марка принято в план. Сейчас repo остаётся private. Смена публичности — отдельное внешнее действие, не часть разрешённого сейчас планирования.

### Зачем

GitHub делает стандартные hosted runners бесплатными в публичных репозиториях. Текущие workflows используют ubuntu-24.04 — подходящий стандартный runner. Это не отменяет расходы Railway, старые начисления, larger runners, отдельные платные продукты и возможные расходы хранения. Публичность Automations сама по себе не делает бесплатными jobs, запускаемые в private Ops или других private caller-репозиториях.

### Конкретные шаги

1. Проверить весь публикуемый охват: main, все девять нынешних веток, доступную историю коммитов и тегов, issues/comments, PR, Actions logs/artifacts, изображения и Git LFS.
2. Особое внимание исторической ветке infra/work-github-upload: там есть screenshots, railway-inventory и отчёты App/OAuth. Служебные ID и hash сами по себе не секреты, но файлы могут раскрывать устройство приватных проектов. Проверять фактическое содержимое, а не только название.
3. Уже сделанная в этом исследовании ограниченная проверка текстов main не обнаружила PEM private-key header, типичных GitHub token literals и длинных строк в некоторых secret assignments. Это **не полная проверка истории**, не проверка screenshot и не разрешение объявить «секретов точно нет».
4. При обнаружении действующего секрета сначала отозвать/заменить только скомпрометированный credential; исправление последнего коммита не удаляет его из истории. Не переписывать историю или удалять доказательства автоматически.
5. Проверить workflows для публичного контекста: PR из fork без provider credentials; сохранение owner/main admission для служебных команд; environment с токеном не открывать чужому коду. Все три нынешних workflow закрепляют actions по SHA.
6. Проверить, что публикация не делает открытым журнал пользовательских payload. Рабочие bytes и SQLite остаются вне репозитория конфигурации; если Ops journal будет в ветке публичного repo, его допустимое содержимое проверить отдельно.
7. Сменить visibility поддержанным административным интерфейсом. Нынешний GitHub connector читает admin=true, но не предоставляет операции смены visibility. Наличие прав аккаунта не заменяет отсутствующий метод инструмента.
8. Прочитать visibility=public обратно и проверить анонимную доступность репозитория. Проверить правила веток после смены, доступ workflow к необходимым ресурсам и один релевантный public CI run.
9. Не обещать нулевой общий счёт GitHub: отдельно наблюдать storage/другие private workflows и actual billing.

**Приёмка P:** весь известный публикуемый охват проверен; выявленные замечания разрешены; visibility=public подтверждена; актуальный стандартный CI прошёл. Публичность не распространяется на репозитории, в которые потом загружаются файлы.

Этап P можно делать рядом с основным маршрутом после разрешения реализации. Он не должен превращаться в месячную пересборку всех репозиториев и не является условием первого upload.

## 9. Расходы и календарь

### GitHub

Для публичного Automations стандартный ubuntu runner — бесплатный compute. Текущая приватная версия расходует включённые лимиты/платный usage аккаунта. CI использовать для подготовленного изменения, не гонять зелёные проверки без новой причины. Documentation-only сохранение этого плана не попадает в path filters исходного CI; служебные команды и hosted jobs сейчас не запускаются.

### Railway

Новая подписка не нужна: существующий workspace уже использует Railway. По официальной опубликованной сетке: RAM $10/GB/месяц, CPU $20/vCPU/месяц, volume $0.15/GB/месяц, egress $0.05/GB. Применимость к аккаунту и фактический счёт проверяются отдельно.

Иллюстративные сценарии постоянной работы одного n8n:
- средние 0.5 GB RAM + 0.02 vCPU + 1 GB disk: около $5.55/месяц плюс egress;
- средние 0.75 GB + 0.05 vCPU + 1 GB disk: около $8.65/месяц плюс egress;
- непрерывное потребление на нынешних пределах 1 GB + 0.5 vCPU + 1 GB disk: около $20.15/месяц плюс egress.

Это расчёты ресурсов, не замеры новой версии, не новый бюджет и не фиксированный тариф. Базовая подписка учитывается по правилам общего usage, не прибавляется второй раз механически. Нынешнее исследование не читало актуальный bill и не создаёт разрешения автоматически потратить все предельные суммы.

Предлагаемый ориентир для обсуждения при запуске: целевой расход n8n до $10/месяц при проверенном запасе ресурсов. Если необходимы большие расходы — показать конкретную дельту, а не молча добавлять сервис или RAM. Уже разрешённые расходы повторно не согласовывать. Старый пилот $1 / 2 часа не выдавать за бессрочный бюджет.

Первую версию оставить постоянно доступной. Sleep/serverless рассматривать только после отдельного реального cold-start/upload теста: иначе экономия может вернуть 502 и проблемы с OAuth.

### Сроки и контроль исполнения

Достоверный календарный срок сейчас не установлен: исходный Deploy admission имеет нераскрытую причину отказа; доступность data path нового Work также требует подтверждения. Обещание конкретного количества часов до результата при этих неизвестных было бы выдумкой.

План задаёт порядок и контрольные результаты:
- после S1 — постоянный сервер;
- после S2 — первая полезная выгрузка из Work в разные repo;
- после S3 — принятый массовый пакет;
- после S4 — проверенное восстановление;
- после S5 — реальные правила целевых repo;
- после S6 — повторяемость новых сессий и эксплуатация;
- P — отдельно подтверждённый public/CI результат.

После разрешения реализации исполнитель проходит этапы сам в уже данных границах. Внешний отказ обозначается сразу с точным действием и доказательством. Ожидание внешнего механизма не маскируется дополнительными source-спринтами.

## 10. Что остаётся неизвестным и не объявляется проверенным

- Причина автоматического отказа исходного Deploy.
- Устойчивый HTTPS data path из нынешней и следующих сред Work; таймаут нынешнего GET не даёт полного диагноза.
- Native import/execution новой JSON-схемы в установленном n8n:2.46.6.
- Пиковая RAM, native binary temp cleanup и время новой 100-файловой версии.
- Автоматическая recovery во всех существенных фазах; сейчас в части фаз есть только безопасная остановка.
- Silent refresh реального OAuth в свежих Work после срока access token.
- Поддержка PR/workflow files и Git mode при текущих App permissions.
- Полная чистота истории/изображений/logs для открытия репозитория.
- Актуальное денежное списание CI/Railway и точный суточный расход постоянной версии.
